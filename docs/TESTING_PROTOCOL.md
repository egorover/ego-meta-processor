## 1. Архитектура тестовой среды

Тестирование разделено на три изолированных контура для обеспечения чистоты данных и безопасности проверок деградации.

| Сценарий | Файл / ID | Назначение | Контакты-маркеры |
| :--- | :--- | :--- | :--- |
| **Основной процесс** | `3.06.10 Qwe - OP - Order Processing v2 (improved final)` | Боевой воркфлоу обработки заказов | Реальные клиенты |
| **Здоровый прогон** | `3.06.11 Qwe - TR - Test Runner` | Регрессия бизнес-логики, happy path, валидация | Обычные контакты (`alexey@test.ru`, `boris@test.ru` и др.) |
| **SBT (Smoke Broken Test)** | `3.06.12 Qwe - SBT - Smoke Broken Tests` | Проверка обработки ошибок, деградации, circuit breaker | Префикс `sbt_` (`sbt_fedor@test.ru`, `sbt_switch@test.ru`) |

> ⚠️ **Критическое правило:** Никогда не запускайте SBT вместе со здоровым прогоном. Никогда не оставляйте среду сломанной после теста.

## 2. Здоровый прогон (Регрессия)

**Цель:** Убедиться, что все штатные сценарии работают корректно, данные записываются в NocoDB без ошибок.

### Порядок действий
1. Откройте воркфлоу **3.06.11 Qwe - TR - Test Runner**.
2. Убедитесь, что основной воркфлоу **3.06.10 Qwe - OP** открыт в соседней вкладке и нода «Приём заказа» находится в режиме **Listen for Test Event**.
3. Нажмите **Test workflow** (или Execute Workflow).
4. Дождитесь завершения всех нод.
5. Проверьте ноду **«Сводка результатов»**: все коды должны быть `200`, `422`, `413`, `508` (ожидаемые ошибки валидации), но **не** `500`/`502`.

### Ожидаемые результаты в таблицах NocoDB

#### Таблица `orders`
*   Заказы с адресом и товарами из каталога → `status = done`, `review_reason` пустое.
*   Заказы без адреса → `status = needs_review`, `review_reason = no_address`.
*   Заказы с неизвестными товарами → `status = needs_review`, `review_reason = unknown_items:N`.
*   Дубликаты → новая строка **не создается**.
*   Поля `error_code`, `error_message`, `retry_payload` → **пустые** (так как модель работает штатно).

#### Таблица `log`
*   Стадии `validate/ok`, `dedup/ok`, `llm/ok`, `parse/ok/done`.
*   `http_code = 200` для успешных заказов.
*   `http_code = 422/413/508` для отклоненных на валидации.
*   Колонка `error` заполнена **только** для rejected-стадий.

## 3. SBT: Smoke Broken Tests (Проверка деградации)

**Цель:** Подтвердить, что система корректно обрабатывает сбои, пишет коды ошибок в лог и отправляет алерты.

### ⚠️ ЖЕЛЕЗНОЕ ПРАВИЛО ПОСЛЕДОВАТЕЛЬНОСТИ
**Никогда не ломайте две вещи одновременно!**
1. Сломай компонент А → Раскомментируй тест А → Запусти → Проверь → Почини А → Закомментируй тест А.
2. Только потом: Сломай компонент Б → Раскомментируй тест Б → Запусти → Проверь → Почини Б → Закомментируй тест Б.

### Тест T6_SBT: Авария LLM (Transport Error)

**Подготовка:**
1. Перейдите в **Credentials** → **OpenAI account** (YandexGPT).
2. Измените одну букву/цифру в API-ключе. Сохраните.
3. Откройте воркфлоу **3.06.12 Qwe - SBT**.
4. В ноде **«Генерация SBT»** раскомментируйте строку T6:
   ```javascript
   { label: 'T6_SBT — авария модели → 502', customer: 'SST_Fedor', contact: 'sbt_fedor@test.ru', ... }

   Сохраните ноду. 

**Запуск:** Запустите `3.06.12 Qwe - SBT`.

**Ожидаемый результат:**
* **orders:** Новая строка НЕ создана (заказ отсечен до создания).
* **log:** Одна запись: `stage = validate, status = rejected, error = processing_disabled, http_code = 503`.
* **Output SBT:** Код ответа `503`.

**Откат (ОБЯЗАТЕЛЬНО):**
1. Верните `orders_enabled = true` в NocoDB settings.
2. Закомментируйте строку `T7` обратно.

## 4. Чек-лист чистоты данных
После каждого цикла тестирования (здоровый + SBT) выполните очистку:
* Удалены все строки из `orders` с контактами, содержащими `sbt_`.
* Удалены все строки из `orders` с контактами тестовых пользователей (`spam@test.ru`, `test_long@test.ru` и т.д.), если они не нужны для демо.
* В `settings` проверено, что `orders_enabled = true`.
* В `Credentials` проверен корректный API-ключ YandexGPT.
* В воркфлоу `3.06.12 Qwe - SBT` все тестовые строки закомментированы.
* Воркфлоу `3.06.10 Qwe - OP` сохранен и не активен (`active = false`), если не используется в проде.

## 5. Типичные ошибки и их решения

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| **ERR_DATABASE_OP_FAILED** при `PATCH` | Не создана колонка `review_reason` или `http_code` | Создайте колонки в NocoDB до запуска |
| Тест `T6` не падает, а проходит успешно | Ключ не сломан или кэш кредов n8n | Пересохраните Credential, перезапустите n8n |
| Тест `T7` создает заказ вместо отказа | `orders_enabled` не изменен или кэш настроек | Проверьте значение в NocoDB, обновите страницу |
| Дубликаты создают новые строки | Изменился текст/контакт (другой `idempotency_key`) | Используйте байт-в-байт идентичные данные для `T5` |
| Лог пустой или неполный | Основной воркфлоу не слушал вебхук во время теста | Всегда держите `3.06.10 Qwe - OP` в режиме *Listen* при запуске раннеров |

## 6. Глоссарий терминов
* **SBT (Smoke Broken Test)** — изолированный набор тестов для проверки путей обработки ошибок.
* **Circuit Breaker** — механизм аварийного отключения приема заказов через флаг в БД.
* **Review Reason** — машиночитаемая причина статуса `needs_review` (прозрачность для менеджера).
* **Idempotency Key** — уникальный ключ запроса, предотвращающий дублирование заказов.
* **Transport Error** — ошибка связи с LLM (таймаут, 401, 403, 429).
* **Schema Error** — ответ от LLM получен, но не соответствует ожидаемой структуре JSON.
