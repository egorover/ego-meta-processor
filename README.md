## 1. Что это

**EgoMeta Processor** — пайплайн приёма заказов, изложенных свободным текстом, и извлечения из них структурированных данных: состав заказа (SKU и количество), адрес доставки, срочность. Разбор выполняет ИИ-агент на базе YandexGPT (OpenAI-совместимая нода в n8n).

### 1.1. Состояние и статус

**Статус: MVP production-grade качества.** Все функциональные требования ТЗ выполнены и подтверждены тестами; внедрены практики промышленной разработки — полная наблюдаемость всех исходов, обработка штатных и критических отказов, идемпотентность, аварийный выключатель. Система готова к **опытной эксплуатации** на ограниченном трафике под наблюдением дежурного. Переход к полной промышленной эксплуатации требует инфраструктурного обвеса (CI/CD, резервирование, безопасность, бэкапы) — см. [`docs/ROADMAP.md`](docs/ROADMAP.md).

Честная самооценка по критериям production-готовности:

| Критерий | Статус | Комментарий |
|---|:---:|---|
| Функциональные требования ТЗ | ✅ | Все пункты выполнены, подтверждены тестами (TR / SBT / EW) |
| Наблюдаемость (логи, алерты) | ✅ | Triple Journaling, Telegram-алерты, Error Workflow |
| Обработка штатных и критических отказов | ✅ | Красная ветка агента + отдельный Error Workflow |
| Идемпотентность и лимиты частоты | ⚠️ | Работают; нет unique-констрейнта на уровне БД — теоретическая гонка при строгом параллелизме |
| Метрики и мониторинг стоимости | ⚠️ | Есть событийный лог и `cost_rub`; нет дашбордов и бюджетных алертов |
| Автоматизированная регрессия (CI/CD) | ❌ | Тесты ручные (race condition тестового вебхука); автотесты — в v.4 |

| Безопасность (TLS, секреты, PII) | ❌ | localhost/http; токены в локальных скриптах (вне git) |
| Бэкапы / Disaster Recovery | ❌ | Не формализованы |

### 1.2. Ключевые возможности (v.3)

* Вебхук → валидация с осмысленными HTTP-кодами (`422`, `413`, `508`, `503`);
* идемпотентность: derived-ключ + **материализация статуса `duplicate`** (аудит-строка в `orders`);
* лимит частоты: 20 заказов/час на контакт (`rate_limited`);
* двухшаговая запись: `processing` → `done` / `failed` / `needs_review`, с `retry_payload` при сбое;
* LLM-разбор (YandexGPT): сопоставление с каталогом, извлечение адреса и срочности, наценка +15% за срочность;
* **Triple Journaling**: гарантированное логирование всех исходов (`validate` → `dedup` → `llm` / `parse`);
* прозрачная очередь ревью с машиночитаемым `review_reason`;
* **Error Workflow (3.06.14)**: перехват необработанных инфраструктурных крахов;
* Telegram-алерты дежурному при сбоях и критических состояниях.

### 1.3. Требования к инфраструктуре

> ⚠️ Для корректной работы необходимы:
> * настроенный Telegram-бот и подключённый чат дежурного;
> * **в РФ:** рабочий VPN-сервис на сервере (доступ к Telegram Bot API) либо развёртывание на зарубежном VPS;
> * стабильный outbound-доступ к YandexGPT API и NocoDB.

## 3. Ключевые архитектурные решения

1. **Triple Journaling.** Ноды записи в `log` расположены **до** точек ветвления бизнес-логики (`validate` → `dedup` → `llm`/`parse`). Любой исход — включая `rejected`, `duplicate`, `rate_limited` — гарантированно оставляет след в журнале. Дефект v.2 (потеря логов отсечённых потоков) устранён полностью.
2. **Материализация дублей.** Повторный запрос с тем же idempotency-ключом создаёт аудит-строку со статусом `duplicate` и ссылкой на исходный заказ в `retry_payload`; модель не вызывается. Экономия ресурсов и прозрачность для дежурного (п.11 ТЗ).
3. **Детерминированная классификация ошибок LLM.** Транспортные, форматные и схемные отказы классифицируются regex-парсером сообщения об ошибке, а не вторым вызовом модели: без шума и лишних затрат.
4. **Изоляция тестовых контуров.** Контакты с префиксом `sbt_` не загрязняют боевые данные; TR и SBT никогда не запускаются совместно.
5. **Review Reason.** Каждый `needs_review` сопровождается машиночитаемой причиной (`no_address`, `unknown_items:N`, `llm_failed:*`) — очередь ревью аудируема и пригодна для автоматических дашбордов.
6. **Семантика Error Workflow.** Обработанные отказы (модель) идут по красной ветке агента с ответом 502; EW срабатывает **только** на необработанные крахи (БД, сеть, падение ноды). Разделение ответственности «бизнес-ошибка / инфраструктурная авария».

## 4. Ограничения и план развития

| Ограничение | Наблюдаемый эффект | План |
|:---|:---|:---|
| Ручное автотестирование | Прогоны TR/SBT нестабильны из-за race condition: вебхук возвращает ответ до записи в NocoDB | v.4: боевой вебхук + асинхронный polling результатов (см. TESTING_PROTOCOL v1.2.1, разд. 1) |
| Нет unique-констрейнта на `idempotency_key` | Теоретическая гонка дублей при строгом параллелизме | Пост-MVP: констрейнт на уровне БД |
| Ревью-очередь без UI | Менеджер работает напрямую в NocoDB | Пост-MVP: React/Retool UI |
| Каталог цен зашит в промпт | Изменение цен требует правки воркфлоу | Пост-MVP: продуктовая таблица `prices` |
| Нет дашбордов метрик | Стоимость и SLA контролируются вручную по логам | Пост-MVP: Grafana + бюджетные алерты |

Полная дорожная карта: [`docs/ROADMAP.md`](docs/ROADMAP.md).

## 5. Тестирование

**Полный протокол:** [`docs/TESTING_PROTOCOL.md`](docs/TESTING_PROTOCOL.md) (v1.2.1).

**Критерии приёмки v.3:** код HTTP-ответа; состояние таблицы `orders` (статус + поля); наличие записей в `log` (гарантировано Triple Journaling); Telegram-алерт при сбоях.

> ⚠️ В v.3 для детерминированных результатов рекомендуется **ручное тестирование** готовыми PowerShell-командами из протокола: тестовый вебхук n8n возвращает ответ до завершения записи в NocoDB, что создаёт race condition при автопрогонах. Полноценное автотестирование — цель v.4.

**Статусы, покрытые тестами (п.11 ТЗ):** `done`, `needs_review`, `duplicate`, `failed`, `processing` (индуцированный крах для демонстрации EW).

## 6. Развёртывание

1. **Импортировать** воркфлоу из `workflows/`: `3.06.11`, `3.06.12`, `3.06.13`, `3.06.14`. Файл `3.06.10` из архива **не импортировать**.
2. **Настроить credentials:** NocoDB API Token; OpenAI account (endpoint YandexGPT); Telegram Bot API; Header Auth для вебхука.
3. **Подключить Error Workflow:** в `3.06.13` → Workflow settings → Error Workflow = `3.06.14 Qwe - EW - Error Workflow`. Сам EW должен быть Published и Active.
4. **Подготовить NocoDB:** таблицы `orders`, `log`, `settings`; колонки `orders.review_reason` (Text), `log.http_code` (Number).
5. **Обеспечить доступ:** VPN на сервере для Telegram (РФ); outbound к YandexGPT API.
6. **Вебхуки:** тестовый `/webhook-test/order-v2` (режим Listen for Test Event); боевой `/webhook/order-v2` (требует тумблер Active).

## 6. Развёртывание

### 6.1. Импорт воркфлоу

Импортировать из `workflows/`:
- `3.06.11_Qwe_TR_Test_Runner.json` (тестовый контур)
- `3.06.12_Qwe_SBT_Smoke_Broken_Tests.json` (тесты деградации)
- `3.06.13_Qwe_OP_Order_Processing_v3.json` (действующий боевой)
- `3.06.14_Qwe_EW_Error_Workflow.json` (обработка крахов)

Файл `3.06.10_*.json` из `workflows/archive/` **не импортировать** — это архивная точка сравнения v.2 → v.3.

### 6.2. Настройка Credentials в n8n

Все секреты хранятся в **Credentials** n8n (шифруются в БД, не попадают в JSON воркфлоу и git):

| Credential | Назначение | Используется в |
|:---|:---|:---|
| **NocoDB API Token** | Доступ к таблицам `orders`, `log`, `settings` | 3.06.13 (все PATCH/GET), 3.06.11, 3.06.12 |
| **OpenAI account** (endpoint YandexGPT) | Вызов модели `yandexgpt/latest` | 3.06.13 (ИИ-агент) |
| **Telegram Bot API** | Отправка алертов дежурному | 3.06.13 (красная ветка), 3.06.14 (EW) |
| **Header Auth** | Проверка входящих запросов на вебхуке | 3.06.13 (Приём заказа) |

> ⚠️ **Никогда не экспортируйте credentials.json** — он добавлен в `.gitignore`. При переносе проекта на другой сервер credentials настраиваются заново через UI n8n.

### 6.3. Переменные окружения (`.env`)

Параметры конфигурации (не секреты, но меняются между окружениями) вынесены в `.env` в корне проекта.

1. Скопируйте шаблон:
   ```bash
   cp .env.example .env
2. Заполните реальные значения (ID таблиц, URL, workspace/project ID). Секреты (токены) в `.env` не указываются — они хранятся в Credentials n8n.

3. Убедитесь, что `.env` добавлен в `.gitignore` (уже сделано). Никогда не коммитьте `.env`.

### 6.4. Подготовка NocoDB
Создать таблицы: `orders`, `log`, `settings`.

**Обязательные колонки:**
*   `orders.review_reason` (Text)
*   `orders.retry_payload` (JSON / Text)
*   `orders.error_code` (Text)
*   `log.http_code` (Number)
*   `log.error` (Text)

В таблице `settings` создать запись с полем `orders_enabled = true` (Circuit Breaker).

### 6.5. Подключение Error Workflow
1. Убедитесь, что **3.06.14 Qwe - EW** находится в статусах *Published* и *Active* (зелёный тумблер).
2. В **3.06.13 Qwe - OP** откройте *Workflow settings* (стрелка вниз у кнопки *Publish*).
3. В поле *Error Workflow* выберите **3.06.14 Qwe - EW - Error Workflow**.
4. Сохраните изменения.

### 6.6. Требования к инфраструктуре
⚠️ **Для РФ:** на сервере должен быть установлен рабочий VPN-сервис для доступа к Telegram Bot API. Альтернатива — развёртывание на зарубежном VPS.

**Outbound-доступ:**
*   YandexGPT API (`api.cloud.yandex.net`)
*   NocoDB (`порт 8080`)
*   Telegram Bot API (`api.telegram.org`)

### 6.7. Вебхуки

| Режим | URL | Когда использовать |
|---|---|---|
| **Тестовый** | `/webhook-test/order-v2` | Ручное тестирование через «Listen for Test Event» |
| **Боевой** | `/webhook/order-v2` | Production (требует тумблер Active = ON) |

### 6.8. Проверка развёртывания
После настройки запустите ручной тест из `docs/TESTING_PROTOCOL.md` (раздел 2, строка 3 — E2 с адресом). 

**Ожидаемый результат:** строка в `orders` со статусом `done`, полная цепочка в `log` (`validate` → `dedup` → `llm` → `parse`).
